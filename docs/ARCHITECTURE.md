# Архитектура

```
 Windows-игра (PE x86-64)            Linux-программа (ELF x86-64)
          │                                     │
 ┌────────▼─────────┐                           │
 │ 3. Windows API   │  загрузчик PE, ntdll/kernel32/… (свой или Wine — решение на этапе 5)
 │ 4. D3D11 → Metal │  очередь команд → поток подачи в Metal (этап 6)
 └────────┬─────────┘                           │
          └──────────────┬──────────────────────┘
                ┌────────▼─────────┐
                │ 2. linux-abi     │  ELF, стек процесса, системные вызовы Linux → Darwin
                └────────┬─────────┘
                         │ Engine::run() → Exit::Syscall / Fault / …
                ┌────────▼─────────┐
                │ 1. x86-cpu       │  декодер, состояние CPU, движки: интерпретатор (сейчас), JIT (этап 3)
                └────────┬─────────┘
                ┌────────▼─────────┐
                │ guest-mem        │  адресное пространство гостя (общая база для слоёв 1 и 2)
                └──────────────────┘
```

Каждый слой — отдельный crate, граница — узкий интерфейс:

* **Слой 1 ↔ 2:** трейт `x86_cpu::Engine`. CPU ничего не знает об ОС: инструкция
  `syscall` возвращает `Exit::Syscall`, слой 2 обслуживает вызов и продолжает.
  Любой движок (интерпретатор, свой JIT, порт FEXCore) подключается через этот трейт.
* **Память:** `guest_mem::GuestMemory` — одна резервация хоста на 32 ТБ,
  `host = base + guest`. JIT будет держать `base` в закреплённом регистре Arm64.

## Почему так

* **Почему Windows идёт через Linux-слой.** Античиты с поддержкой Linux (EAC, BattlEye)
  работают по схеме Proton: Windows-игра под Wine + нативная Linux-библиотека
  античита. Чтобы такая библиотека вообще могла загрузиться, нужен слой Linux x86-64.
  Окончательное решение — этап 5/7.
* **Почему блоки.** Декодирование один раз на блок и кэш по адресу делают
  интерпретатор быстрым, а блок одновременно служит единицей JIT-компиляции.
* **Почему ленивые флаги.** Большинство результатов флагов никто не читает. Мы храним
  (операцию, операнды, результат) и вычисляем флаг по запросу; для `cmp`+`jcc` есть
  быстрый путь. Тот же приём понадобится и в JIT.
* **Страницы 16 КБ против 4 КБ.** Гостевой код никогда не исполняется напрямую, поэтому
  все хост-страницы гостя — RW, а права гостя ведутся программно в списке VMA.

## Распределение работы по ядрам (план)

| Решение | Этап | Что меряем |
|---|---|---|
| Фоновая JIT-компиляция, интерпретатор как запасной путь | 3 | время ожидания компиляции в горячем потоке (сейчас декодирование = 0.02 % времени) |
| QoS: горячие потоки `USER_INTERACTIVE` (P-ядра), компилятор `UTILITY`/`BACKGROUND` (E-ядра) | 3–4 | на каких ядрах реально исполняются потоки, задержки |
| Очередь команд D3D11 → поток подачи в Metal | 6 | время, которое поток рендера стоит на вызовах графики |

M5 в этой машине: 4 производительных и 6 энергоэффективных ядер (`hw.perflevel0/1`).
