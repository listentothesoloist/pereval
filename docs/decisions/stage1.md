# Этап 1: итоги и решения

## Что сделано

| Часть | Где | Статус |
|---|---|---|
| Адресное пространство гостя | `crates/guest-mem` | одна резервация хоста, `host = base + guest`, учёт VMA, страницы 4 КБ поверх 16 КБ |
| Декодер x86-64 | `crates/x86-cpu/src/decode.rs` | префиксы, REX, ModRM/SIB, RIP-relative, однобайтовая и 0F карты, SSE/SSE2 |
| Интерпретатор | `crates/x86-cpu/src/interp.rs`, `sse.rs`, `flags.rs` | целочисленный набор, строковые операции, SSE/SSE2 (подмножество), ленивые флаги, кэш блоков |
| Загрузчик ELF | `crates/linux-abi/src/elf.rs` | ET_EXEC и static-PIE, начальный стек по psABI (argc/argv/envp/auxv) |
| Системные вызовы Linux | `crates/linux-abi/src/syscall.rs` | ~35 вызовов: read/write/writev, mmap/munmap/mprotect/brk, arch_prctl, clock_gettime, uname, getrandom… |
| Запуск | `crates/xrun` | `xrun [--strace] [--stats] [--clear-env] prog args…` |

Цель этапа достигнута: статический `hello world` для Linux x86-64 (голые системные
вызовы, musl + `printf`, static-PIE) работает, и тесты это подтверждают.

## Как проверяется корректность

1. **Сверка с Rosetta 2** (`tools/oracle`, `crates/x86-cpu/tests/oracle.rs`).
   Оракул собран как x86-64 программа для macOS и работает под Rosetta, то есть на
   независимой промышленной реализации x86-64. Он исполняет настоящие инструкции на
   граничных и случайных входах: 318 форм инструкций, 15 264 случая. Интерпретатор
   должен совпасть по всем регистрам и всем *определённым* флагам. Сейчас совпадает 100 %.
2. **Сквозные тесты** (`crates/xrun/tests/guest.rs`). Настоящие ELF-файлы запускаются
   через `xrun`. У бенчмарка вывод сверяется с тем же исходником, собранным нативно
   под arm64.
3. Юнит-тесты декодера, памяти, SSE и errno.

### Найденные расхождения с Rosetta

* **Флаги `CMPXCHG`.** Rosetta выставляет CF/SF/AF/PF/OF по `dest − rax`. В SDM
  написано «как `CMP accumulator, dest`», эмуляторы KVM (`em_cmpxchg`) и Bochs
  тоже считают `rax − dest`. Реализовано по SDM, а в сверке для этой инструкции
  сравнивается только ZF.
* **Старшие биты при 32-битном `CMPXCHG r32, r32`.** Три источника дают три ответа:
  Rosetta при успехе обнуляет старшую половину RAX; QEMU (исправление 2022 года) при
  неудаче не трогает приёмник; буквальное чтение псевдокода SDM (у нас) при неудаче
  пишет и RAX, и приёмник, а при успехе пишет только приёмник. Сверяются младшие
  32 бита. **Открытый вопрос:** окончательный ответ даст запуск `tools/oracle/oracle.c`
  на настоящем Intel/AMD (код переносим на Linux x86-64).

## Замеры (M5, macOS 27.2, `tests/guest/src/bench.c 8`, лучшее из 3)

| Вариант | Время | Относительно нативного | Относительно Rosetta |
|---|---:|---:|---:|
| нативно arm64 | 25 мс | 1.0× | 0.7× |
| Rosetta 2 (x86-64 macOS) | 36 мс | 1.4× | 1.0× |
| **xrun, интерпретатор** | 1771 мс | **70.6×** | **49.9×** |

Интерпретатор выдаёт **325 млн гостевых инструкций в секунду** (557 млн инструкций
за 1.71 с). Декодирование новых блоков занимает **0.02 %** времени работы, потому
что каждый блок декодируется один раз.

Для игры этого мало: в 50 раз медленнее Rosetta — это неиграбельно даже для
нетребовательной 3D-игры. Нужен JIT.

## Решение: свой JIT, не FEX

**Что дал бы FEX.** FEX — эмулятор x86/x86-64 в пользовательском режиме «для Arm64
Linux» (MIT). Его ценность: зрелый JIT x86-64 → Arm64 (IR, оптимизации, распределение
регистров, эмуляция порядка памяти x86 через LRCPC/LSE), x87 и SSE–AVX, годы отладки
на реальных играх через Proton.

**Почему он здесь не подходит как есть.**

1. **Хост — только Linux.** В README хостом указан Arm64 Linux, macOS среди
   поддерживаемых систем нет. Насколько я понимаю устройство FEX, его слой системных
   вызовов в основном *пробрасывает* вызовы Linux в ядро Linux хоста. На macOS ядра
   Linux нет, и именно этот слой (наш слой 2) всё равно пришлось бы писать самим.
2. **Отделение FEXCore от Linux — это порт, а не подключение.** Ядро JIT опирается на
   Linux-сигналы (обработка ошибок доступа, SMC), на модель памяти и выделение
   кода Linux. На macOS код JIT живёт в `MAP_JIT` с переключением W^X
   (`pthread_jit_write_protect_np`) отдельно для каждого потока. Перенос — это правки
   во многих местах большой кодовой базы на C++, которые придётся поддерживать
   против основной ветки. Замерить FEX на этой машине нельзя: он здесь не собирается
   и не запускается. Это и есть результат проверки.
3. **Требование «модули можно заменить своими».** У нас граница слоя 1 — трейт
   `Engine` (запустить гостевой код → `Exit::Syscall`/`Fault`/…). FEX устроен иначе:
   CPU и Linux-ABI в нём тесно связаны. Подогнать его под нашу границу = тот же порт.
4. **Фоновая компиляция ложится на наш дизайн.** Пункт 2 выше одновременно и
   возможность: на macOS запись в JIT-память разрешается отдельно для каждого потока,
   поэтому фоновый поток-компилятор пишет код, а горячий поток в это время его
   исполняет. Интерпретатор уже работает с блоками, а блок и есть единица компиляции.
   Пока блок компилируется, горячий поток исполняет его интерпретатором — это прямо
   требование архитектуры.

**Цена своего пути (честно).** JIT уровня FEX/Rosetta — это годы. Нужен JIT, который
даёт *сопоставимый* порядок скорости на целочисленном коде:

* базовый шаблонный JIT (каждая инструкция → готовый фрагмент Arm64, регистры гостя
  в регистрах хоста, флаги лениво или через NZCV, связывание блоков): по моей оценке
  в 10–30 раз быстрее интерпретатора, то есть 2–5× от Rosetta;
* затем удаление мёртвых флагов, сквозные суперблоки, регистровый аллокатор по блоку.

Если на этапе 3 свой JIT упрётся в стену и не выйдет за 2–5× от Rosetta, вопрос о
порте FEXCore снова откроется. Граница `Engine` это позволяет, но тогда это будет
порт с собственным слоем сигналов и памяти, а не просто «взять FEX».

## Ограничения, которые остаются сознательно

* Только статические ELF (динамический загрузчик — этап 2).
* x87 не реализован: `printf("%f")` в musl идёт через `long double` и упадёт с
  `SIGILL: unimplemented instruction: x87` (этап 2). Бит FPU в CPUID выставлен,
  потому что он входит в базовый x86-64.
* AVX/VEX, SSSE3/SSE4 (0F 38/0F 3A) не реализованы и в CPUID не объявлены.
* Сигналы: `rt_sigaction` принимается, но обработчики не вызываются (этап 4). Сбой
  гостя завершает процесс с кодом 128+сигнал и диагностикой.
* Однопоточность; `LOCK` пока не атомарен (этап 4).
* Самомодифицирующийся код: блоки сбрасываются на `mmap/munmap/mprotect`, но запись
  в уже декодированный код не отслеживается (этап 3, вместе с JIT).
* Права гостя на страницы проверяются только при выборке кода (NX). Записи в
  read-only страницы не ловятся, потому что хост-страницы всегда RW (это следствие
  страниц 16 КБ против 4 КБ, см. `guest-mem`).
* `TCGETS` возвращает нулевую `termios` (перевод флагов macOS ↔ Linux — этап 2).

## Оценка этапа 2 (файлы, mmap, время, окружение → busybox)

Реалистичный объём — **1–2 недели** работы в таком же темпе:
openat/stat/fstat/newfstatat (+перевод `struct stat`), getdents64, lseek, pread/pwrite,
dup/dup2/dup3, pipe, fcntl, ioctl/termios, getcwd/chdir, readlink (`/proc/self/exe`),
fork/execve/wait4 (busybox `sh` без них бесполезен; fork на macOS — отдельная задача),
таблица дескрипторов, x87 для `printf("%f")`. Самое рискованное — `fork` и `execve`
поверх одного хост-процесса с резервацией памяти. План: настоящий `fork()` хоста
(резервация наследуется копированием при записи) и проверка на busybox `ash`.
Реалистично.
